# read-commits

The release-notes skill does not run a command itself. It is given a list of commits as text. That text has the same shape as the output of `git log --oneline`, so that is the command this file describes. For rule 3 of the skill (checking a commit against its description), the related command is `git show <hash>`.

## Command run

`git log --oneline -10`, run in this repo on 2026-09-19.

## What the output looks like

- The output has one line per commit, and 10 lines because of `-10`.
- Each line is a 7-character hash, a single space, and then the subject line of the commit message.
- There are no dates, authors, or commit bodies. `--oneline` leaves them out.
- The commits are listed newest first.

## What the messages look like

- The messages are informal and hand-typed. Most start with "updated" or "edited", for example "updated CHANGELOG".
- Most of the messages name internal project files such as README, CHANGELOG, findings, or decisions. Almost all of these 10 commits are project-meta changes that the skill's rule 4 says to skip.
- One commit bundles several changes into one line: `1b78776` lists four separate changes joined by commas.
- One line is a merge commit, `3d3a8a4`. It is generated by GitHub ("Merge pull request #7 from ...") and looks different from the hand-written messages. The skill's rules do not mention merge commits.
- The tense is not consistent across the project. These 10 messages are past tense ("updated", "edited", "wrote"), but the messages in `evals/cases/release-notes-20.md` include imperative ones such as "Fix skill format" and "Take Book Recommendations project offline". The skill has to convert these to past tense (rule 7).
- `db8e3c1` has a double space in "eval-related  README". The tool prints messages as typed and does not clean them up.

## Order

`git log` prints newest first. The cases in `evals/cases/release-notes-20.md` are numbered 1 to 20 and their hashes (for example `3087743`) do not exist in this repo, so I could not check whether that numbering is oldest first or newest first. Rule 2 of the skill says to keep the order of the input, so the skill follows whatever order it is given and does not reorder by date.

## What the tool does not tell you

- It does not say what a commit changed in the files. Only `git show <hash>` or `git show --stat <hash>` does that.
- It does not say whether a change is visible to a user of the skill. The skill has to decide that from the message wording alone.
